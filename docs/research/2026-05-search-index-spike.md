## Context

`apps/site` is an Astro static-build SPA. The current MDX corpus lives at
`content/notes/sample-blocks/index.mdx` and `content/notes/sample-mdx-note/index.mdx`
(2 notes, ~hundreds of tokens each). Spec §4.2 requires client-side search
over note prose, with a sub-100ms perceived query latency and reindex
on content change. Plan-challenger R2 #5 (CJK robustness) and #13
(reindex-on-update contract) are explicit gates for the D1b ADR.

The user (`ve11ichor1223`) is CJK-literate; future notes will mix
Chinese/Japanese with English, so tokenizer behavior on `中文笔记` and
`日本語` strings is a hard requirement, not a nice-to-have.

## Candidates

### 1. PageFind

- **Version / activity**: `pagefind` 1.5.2 (2026-04-12), 1.5.0 major
  feature drop 2026-04-06 — actively maintained by CloudCannon.
  Astro adapter: `astro-pagefind` 1.8.6 (2026-04-13).
- **Bundle size**: ~70-100 kB gzip total (search runtime + first index
  chunk) on a typical site; documented ceiling is "under 300 kB total
  network payload for a 10,000-page site, including the library."
  Library JS itself ≈ 30 kB gzip; remainder is index chunks loaded
  lazily.
- **Index size**: chunked by prefix; only ~50 kB of index is fetched
  per query for our 2-note corpus. Extrapolation to 50/100 notes
  remains well under 1 MB total index, with each query loading
  <100 kB.
- **Query latency**: sub-50 ms in 1.5.0 (Web Worker search by default,
  binary-encoded chunks).
- **Build-vs-client**: build-time. Pagefind binary scans the built
  HTML output (post-Astro `astro build`) and emits `_pagefind/`
  chunks. Client only loads chunks on demand.
- **CJK**: 1.5.0 ships **automatic CJK segmentation** via
  `Intl.Segmenter` (both at index time and query time); searching
  "这是一段简单的测试文本" tokenizes identically on both sides.
  No plugin, no config. This is the killer feature vs lunr/flexsearch.
- **Reindex-on-update**: build-time-emit. Rerunning `astro build`
  (or `astro-pagefind` postbuild hook) regenerates `_pagefind/`
  deterministically. Cache-busts via filename hashes. No client-side
  reindex ever needed.
- **Astro integration**: first-party-grade `astro-pagefind` adapter
  with `<Search />` component, dev-mode hot reload of the index UI,
  and `data-pagefind-ignore` attribute. Drop-in.
- **Pros**: out-of-the-box CJK; smallest cognitive load; deterministic
  build artifact; chunked index scales to 10k+ pages.
- **Cons**: requires the Pagefind Rust binary on the build host
  (already common in CI; `astro-pagefind` installs it via npm); index
  cannot be live-mutated client-side (irrelevant for our static-build
  SPA).

### 2. lunr.js

- **Version / activity**: `lunr` 2.3.9 (last published 2020-02; repo
  9.2k stars but 64 tags, 527 commits, no release in ~5 years). Effectively
  in maintenance-only mode. CJK support lives in third-party
  `lunr-languages` (Japanese via TinySegmenter) and `lunr-chinese`
  (Wiredcraft, via nodejieba — Node-only, breaks browser bundles).
- **Bundle size**: ~8.5 kB gzip for `lunr.js` core; +5-10 kB per
  language plugin. CJK adds nodejieba (~2 MB unpacked, server-only)
  or TinySegmenter (~25 kB gzip).
- **Index size**: serialized JSON; for 2-note corpus ~30-50 kB
  uncompressed (~10 kB gzip). Scales linearly; 100 notes ~500 kB
  uncompressed JSON loaded as one blob. No chunking — all-or-nothing
  fetch.
- **Query latency**: sub-100 ms for small corpora; degrades on the
  full-blob load (~500 kB parse cost on cold load) at 100+ notes.
- **Build-vs-client**: hybrid. Idiomatic pattern is build-time
  `lunr.Index.load(serializedIndex)`, but the index JSON must be
  generated by a custom build script (no Astro adapter exists).
- **CJK**: **default tokenizer splits on whitespace + hyphens**, which
  breaks Chinese (no spaces) and treats Japanese as one token. Fix
  requires `lunr-languages/lunr.jp` (TinySegmenter, browser-safe) or
  `lunr-chinese` (nodejieba, Node-only — unusable in client search).
  Plan-challenger R2 #5 hard fail without plugin.
- **Reindex-on-update**: write your own `scripts/build-search-index.ts`
  Astro integration hook to walk MDX → JSON. No first-party tooling.
  Cache-busting via filename hash is DIY.
- **Astro integration**: none official. Community examples exist but
  every one ships its own adapter.
- **Pros**: smallest core JS; well-known; pure-JS so no build-host
  binary.
- **Cons**: dormant project; CJK is a project in itself; no Astro
  adapter; mono-blob index doesn't chunk.

### 3. flexsearch

- **Version / activity**: `flexsearch` 0.8.212 (active, npm shows
  frequent 0.8.x patches through 2026; 13.7k stars). Repo README
  bundle table reflects 0.8.2 (2024) but the npm tag is well past it.
- **Bundle size**: 4.5 kB gzip (light), 11.4 kB gzip (compact),
  16.3 kB gzip (full bundle with document indexes + tag/store).
- **Index size**: ≈2.1 MB for "Gulliver's Travels" full-novel default
  config; ~30% extra for fast-update mode. Our 2-note corpus would
  be <50 kB; 100-note projection ~1-2 MB depending on resolution and
  context-mode.
- **Query latency**: fastest in published JS-search benchmarks
  (Mattermost/HN; sub-10 ms typical).
- **Build-vs-client**: both — `Index.export()` / `Index.import()`
  lets you ship a prebuilt JSON, and the runtime can also build
  client-side. With `fastupdate` flag the index supports incremental
  add/remove without full rebuild.
- **CJK**: ships `Charset.CJK` encoder (renamed from `CjkDefault`
  in 0.8). Behavior: splits on every CJK code point — i.e. character
  unigrams. This works for substring queries but produces lower
  precision than Pagefind's `Intl.Segmenter` word-level segmentation
  (e.g. "中文" matches any string containing 中 or 文 separately).
  Custom tokenizer required for production-grade CJK; community
  patterns (e.g. Ghost PR #22874, issue #137) exist but are user-
  written.
- **Reindex-on-update**: build-time export to JSON + client-time
  `import()` is the documented pattern. Live mutation via
  `index.add(id, doc)` + `index.remove(id)` works in-process but
  doesn't persist; on static SPA we'd rebuild at `astro build` and
  ship a new exported JSON, hash-suffixed for cache-bust.
- **Astro integration**: none official. README lists React/Vue/Gatsby
  but not Astro. Manual integration via Astro integration hook is
  small (~50 LOC) but ours to maintain.
- **Pros**: smallest runtime; fastest queries; supports both CJK and
  Latin in one bundle; live `add/remove` API.
- **Cons**: CJK encoder is character-level (lower precision); no
  Astro adapter; we own the build pipeline; CJK quality requires
  bespoke tokenizer.

(MiniSearch was considered as an optional 4th candidate but is
strictly weaker here: ~10 kB gzip, no CJK tokenizer, no Astro
adapter, mono-blob index — pure downside vs flexsearch.)

## Edge cases

### Non-ASCII / CJK
- **PageFind**: index- and query-time `Intl.Segmenter`. Word-level
  for zh/ja/ko. **PASS plan-challenger R2 #5**.
- **lunr.js**: default whitespace tokenizer breaks CJK. PASS only
  with `lunr-languages` (jp via TinySegmenter, browser-safe) +
  separate Chinese plugin. Two third-party deps + bundle bloat.
- **flexsearch**: `Charset.CJK` works but at character-level (lower
  precision); production-grade CJK needs custom tokenizer. PARTIAL.

### Punctuation-heavy queries (e.g. `'"hello-world" & friends'`)
- **PageFind**: strips quotes/punct on both sides; phrase queries
  via `"…"` syntax supported in 1.5.0 search UI. Robust.
- **lunr.js**: tokenizer splits on `-` so `hello-world` becomes two
  tokens; quotes are dropped. Acceptable for prose, mediocre for
  code-laden notes.
- **flexsearch**: encoders normalize punctuation per preset
  (`LatinAdvanced`/`LatinExtra`); behavior consistent. Robust.

### Reindex-on-update
- **PageFind**: deterministic build-time emit; no client cache to
  invalidate beyond the hashed filenames Astro already produces.
  Maps cleanly onto plan-challenger R2 #13 contract — "rebuild ⇒
  new index ⇒ first page load fetches updated chunks."
- **lunr.js**: DIY build hook writes a single index.json; cache-bust
  is your responsibility.
- **flexsearch**: DIY build hook calls `Index.export()`; same
  cache-bust burden as lunr.

## Recommendation

**PageFind** (via `astro-pagefind` 1.8.6).

Rationale: it is the only candidate that satisfies plan-challenger
R2 #5 (CJK robustness, word-level not character-level) **and** #13
(reindex contract is the build itself, no DIY adapter) without
custom code. The 1.5.0 release closed the prior CJK gap (segmentation
was index-only, queries were not — fixed 2026-04). FlexSearch is the
faster runtime but its CJK story still requires a bespoke tokenizer
we'd have to author + maintain + test, doubling the D1b scope.
lunr.js is dormant and CJK-hostile by default. The Astro adapter
exists, is on 1.8.6 actively, and cuts D2/D3 implementation cost
substantially.

## D1b ADR acceptance criteria

The D1b ADR should lock these measurable targets (verifiable in
D2/D3 PR-level acceptance blocks):

1. **Bundle-size budget**: Pagefind runtime + initial index chunks
   delivered to a cold first paint of the search route ≤ **120 kB
   gzip total** (per Pagefind docs ~70-100 kB typical; 120 kB
   leaves headroom). Measured with `astro build` artifact + gzip.
2. **Index-size budget**: total `_pagefind/` directory ≤ **300 kB
   uncompressed** at 100-note projection (today: 2 notes, expect
   ≤ 30 kB). Single-query chunk fetch ≤ **80 kB gzip**.
3. **Reindex-on-update mechanism**: index regenerated by the
   `astro-pagefind` post-build integration on every `astro build`;
   D1b TC3 test asserts that mutating an MDX file → rerunning
   `astro build` → the resulting `_pagefind/` chunk for the touched
   note differs by content hash. No client-side reindex path is
   permitted (out of scope for static SPA).
4. **CJK tokenizer story** (bonus, plan-challenger R2 #5):
   `Intl.Segmenter`-based segmentation is mandatory; D2 must
   include a regression test indexing `"中文笔记测试"` and
   asserting query "笔记" returns the note (word-level, not
   per-character substring).
