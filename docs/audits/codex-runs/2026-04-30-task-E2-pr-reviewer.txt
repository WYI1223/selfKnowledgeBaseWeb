3. ADR-0006 8-point asymmetry audit (independent reviewer pass)
----------------------------------------------------------------------
#1 Field/attribute audit
   — propsSchema fields are emitted symmetrically by serialize (3 attrs:
     modelUrl/layers/showWeights), consumed symmetrically by parse, asserted
     in the round-trip test (core.test.ts:209-223). No comparator/serializer
     drift surface. PASS.

#2 Status code audit
   — N/A (no HTTP handler).

#3 Strictness audit (load-bearing for this PR)
   — Outer propsSchema.strict() AND inner layerSchema.strict() both present.
     core.test.ts:81-92 lock the inner one with an explicit "INSIDE a layer"
     assertion that fails iff someone removes inner .strict(). The CONTRACT
     also calls this out explicitly (CONTRACT.md:90-92). PASS.

#4 Consumer schema audit
   — propsSchema is single-authority in core/core-definition.ts:14-28.
     Verified no inline z.object redefinitions outside this file in the
     package. NnViz.astro defines a structural Props interface (LayerProp)
     for its prop-typing rather than re-importing the Zod schema — this is
     the pre-existing E1 jupyter Astro pattern and is acceptable because
     Astro pages don't validate at runtime; they receive props from the MDX
     consumer that already passed propsSchema validation upstream. The
     LayerProp.activation literal-union mirrors the schema enum exactly
     ('relu'|'softmax'|'sigmoid'|'tanh'|'linear') — drift would be a pure
     TS error, not a silent strip. NOTE-but-not-blocker.

#5 Algorithm + runtime constant replication audit
   — tf.loadLayersModel is NOT replicated; bridge takes it via injection
     (LoadLayersModelFn) and the production NnViz.tsx wires
     `tf.loadLayersModel` directly (NnViz.tsx:44). Authority = @tensorflow/tfjs.
     Astro topology-layout math (positions/edges/SVG_WIDTH=480/HEIGHT=200/
     RADIUS=6) is replicated between NnViz.astro and NnVizCanvas in
     NnViz.tsx — this is the pre-hydration FOUC-equivalent for SSR vs
     hydrated views. Both use the SAME constants (verified by grep, all
     three numbers match) and the same algorithm. The Astro side renders
     declarative-layers-only as documented (NnViz.astro:8-14); on hydration
     React layers in model-derived topology + status + slider. Markup
     classes match (skb-nn-viz-canvas / -layer / -edge / -label) so the CSS
     applies identically (CONTRACT.md acknowledges hydration-class symmetry).
     This is acceptable because:
       (a) Astro cannot import React,
       (b) the constants are 3 magic numbers, not an algorithm with branches,
       (c) divergence would manifest as a visible FOUC and is detectable.
     E1 jupyter's Jupyter.astro carries the same handcraft pattern. PASS
     with note: if a future tweak adjusts SVG_WIDTH/HEIGHT/RADIUS, both
     files must move together. Not a Wave 2 blocker.

#6 Sister-file documentation audit
   — Cross-doc terminology compared:
       block-nn-viz/CONTRACT.md vs block-jupyter/CONTRACT.md (sister-doc, E1
         viz-block precedent): identical structure (sections "Public surface"

   — In-package terminology: 'nn-viz' (kebab) vs NnViz (Pascal) consistent
     across core-definition / serialize / parse / index / tests / Astro /
     css. Verified by grep. PASS.
