NEW finding #1 — INTERNAL CONTRADICTION inside `ux-ui-lead` definition
   File: agent-contract.md:165-189 (and rendered .claude/agents/ux-ui-lead.md:17-38)

   The agent declares:
     permissions: [read_repo, edit_ui_default, edit_apps_site,
                   dispatch_codex_css_stylist]
   while the description body explicitly says:
     "你**不**调 codex（dispatch 由 orchestrator 集中调度；你 SendMessage
      orchestrator 请求 codex-block-generator clone）。"

   These are mutually exclusive: the permission list **grants** codex dispatch
   capability; the description forbids using it. ADR-0007 D5 (the very ADR
   this PR implements) finalises the decision that **all codex tool patterns
   are orchestrator-only invocations** — `dispatch_codex_*` permissions on
   any non-orchestrator agent are obsolete by D5's own logic.

   The bug originates in ADR-0007 §235 D1 sketch (which was drafted before D5
   was finalised in the same ADR); the sketch retained `dispatch_codex_css_stylist`
   on ux-ui-lead. D5 invalidates that, but the implementation copied the §235
   sketch verbatim into agent-contract.md without reconciling against D5.

   Impact:
     - Asymmetry visible in TWO consumer surfaces (agent-contract.md + the
       generated .claude/agents/ux-ui-lead.md frontmatter+body).
     - When ux-ui-lead spawns and reads its own .md, it gets contradictory
       guidance — same-prompt asymmetry that future teammates will need to
       litigate.
     - This is a **new instance of item #8** (authority document = ADR-0007 D5
       decision; consumer = agent-contract.md ux-ui-lead block; consumer
       fails to honour authority's final decision while honouring its
       earlier sketch).

   Fix: remove `dispatch_codex_css_stylist` from ux-ui-lead permissions in
   agent-contract.md:169 (and let `pnpm generate:configs` regenerate the
   .claude/agents/ux-ui-lead.md). orchestrator retains `dispatch_codex_tools`
   (agent-contract.md:62) which already covers the css-stylist tool.

   This is the kind of asymmetry pr-gate is paid to find. R1 missed it.

NEW finding #2 — Misleading error message + missing test for within-tool_patterns duplicate
   File: scripts/render/types.ts:55-75

   The superRefine duplicate check uses a single `seen` Set across both arrays:

     for (const a of contract.agents) {
       if (seen.has(a.name)) ctx.addIssue({message: `duplicate agent name: ${a.name}`, ...});
       seen.add(a.name);
     }
     for (const tp of contract.tool_patterns) {
       if (seen.has(tp.name)) ctx.addIssue({message: `name collision between agents and tool_patterns: ${tp.name}`, ...});
       seen.add(tp.name);
     }

   Cases:
     (a) duplicate within agents → "duplicate agent name: X"  ✓ (test :83-86)
     (b) cross-collision (agent X + tool_pattern X) → "name collision between
         agents and tool_patterns: X"  ✓ (test :88-91)
     (c) duplicate WITHIN tool_patterns (e.g. two scaffolders both named
         codex-block-generator) → mistakenly reported as "name collision
         between agents and tool_patterns: codex-block-generator" because
         the SECOND occurrence sees the first one in `seen` (which is the
         shared-across-arrays Set). The error text is **wrong** for this
         case. NO TEST covers it.

   This is item-#1 / item-#3 cross-form (added new collection (tool_patterns),
   collision-detection logic was extended but the fan-out of cases was not
   tested symmetrically with the existing case).

   Impact: low severity (validation still fails loudly, just with a misleading
   message), but it is exactly the kind of "added the new branch, didn't
   audit symmetry" asymmetry the audit-checklist exists to catch.

   Fix options:
     (i) accumulate names per-array first, then a final cross-check; emit
         distinct error messages per case ("duplicate tool_pattern name: X" vs
         "name collision between agents and tool_patterns: X"). Add 1 test.
     (ii) keep one Set but record per-name source-array, then differentiate
          in the message.
   Add a test for case (c).

NEW finding #8 — orchestrator → codex prompt-injection contract
   (Pre-Task 0 deep-scan area #5 from the brief.)

   Question raised: when orchestrator runs
     codex exec --profile code-reviewer < /dev/null
   post-D5, where does the ADR-0006 8-point checklist text enter the codex
   prompt?

   Investigation:
     - tmp/codex-profiles.toml: no prompt prose; only model/sandbox/approval.
     - docs/runbooks/codex-tool-invocations.md: human-facing reference; not
       a runtime-loaded prompt source.
     - .codex (per top-level git status untracked): may contain custom
       runtime config, not part of this PR.

   Conclusion: the prompt prose MUST be passed as the second positional
   arg to `codex exec --profile X "<PROMPT>" < /dev/null` (per AGENTS.md:60-64
   examples). The orchestrator is responsible for assembling the prompt
   (including the 8-point checklist + diff context) per invocation.

   This is the same situation as **pre-D5**: even when code-reviewer was a
   teammate, its `.claude/agents/code-reviewer.md` body was a description for
   humans/orchestrator, not a prompt auto-injected into codex. The teammate
   wrapper Claude turn was what assembled the codex prompt.

   Post-D5, the orchestrator-direct path simply removes the wrapper Claude
   turn — orchestrator must now assemble the prompt directly. No new gap
   introduced; the responsibility merely moves from "wrapper teammate's first
   turn" to "orchestrator's Bash invocation".

   docs/runbooks/codex-tool-invocations.md (new) is the orchestrator's
   reference for what to include. The §"ADR-0006 D8 reminder" + per-pattern
   description sections collectively serve as the prompt-template library.
   This is acceptable; no contract gap.

   Recommendation (NON-BLOCKING for this PR; future-Wave 2 work):
   add a short paragraph to the runbook (or to team-operations.md §"Codex
   CLI 调用规范") explicitly stating: "orchestrator MUST pass the per-pattern
   description text + ADR-0006 8-point checklist to `codex exec` as the
   prompt argument; codex profile config carries no prompt prose." This is
   already implied but not explicit. Could be in a follow-up PR — does not
   block this one.
