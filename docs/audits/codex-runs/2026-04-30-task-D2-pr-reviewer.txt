3. Architectural consistency
───────────────────────────────────────────────────────────────────────────
PASS — design deviation from "react-pdf" plan blurb is reasonable.

  • Iframe-based viewer rationale (CONTRACT.md:6-7,60-65 + render-pdf.ts:6-29):
      a. Astro SSR cannot run react-pdf (browser worker thread + canvas).
         renderPdf must be byte-equivalent across SSR + client paths
         (ADR-0006 #5). react-pdf would require two divergent code paths.
      b. Browser-native PDF viewer is universal runtime authority. The
         #page=N fragment is PDF Open Parameters, recognized by all major
         browsers. Failure mode is the browser's empty-doc UI, satisfying
         "errors explicit, not silent" invariant.
      c. ADR-0008 D1 dead-dep: package.json declares only what is imported
         (zod + 2 workspace links); no react-pdf/pdfjs-dist runtime dep.
         Verified via grep: imports in src/ are exactly @skb/block-foundation,
         @skb/design-tokens, zod, vitest (test only) — every one declared.

  • renderPdf single authority (ADR-0006 #5 algorithm replication):
      - render-pdf.ts:43-57 is the single constructor of ${src}#page=${page}
        and the data-attr map.
      - Pdf.tsx:3 + 22 imports & calls renderPdf, then spreads dataAttrs
        + iframeSrc. No inline URL construction.
      - Pdf.astro:2 + 15 same pattern. Both files identical structure.
      - ssr-render.test.ts:25-66 = 5-row corpus pinning iframeSrc / data-
        attrs invariants (default page=1, arbitrary page, special-char src
        passthrough, missing-file passthrough, page-discrimination).
        Drift detector active.

  • Headless purity (ADR-0003):
      - src/core/{core-definition,parse,serialize}.ts import only
        @skb/block-foundation + zod + sibling files. No React, no iframe,
        no @skb/design-tokens. Compliant.
      - src/ui-default/* imports React (Pdf.tsx) + @skb/design-tokens
        (pdf-tokens.ts) only as expected.

  • Self-validating round-trip:
      - serializePdf calls propsSchema.parse(node.attrs) then emits
        String(boolean)/String(number) attrs (serialize.ts:39-54).
      - parsePdf coerces string→{boolean,number} per attr name and validates
        through propsSchema.parse (parse.ts:25-66). Boolean shorthand
        (attr.value===null) only honored for `searchable`; mismatched names
        / null on other attrs throw with explicit messages.
      - Round-trip: serialize emits 'true'/'false'/digit-string, parse
        accepts both shorthand-null AND 'true'/'false' strings → stable.

   #1  Field/attribute audit (comparator/serialize symmetry):
       PASS — propsSchema fields {src,page,searchable} are uniformly
       handled by serializePdf, parsePdf, and tested in core.test.ts:5-50,
       83-152. No comparator function exists in this PR (no marksEqual-
       analogue surface yet).

   #2  Status code audit:
       N/A — TS-only package, no HTTP handlers.

   #3  Strictness audit:
       PASS — propsSchema.strict() at top level; no nested objects in
       schema, so propagation question is moot. core.test.ts:39-43 verifies
       unrecognized_keys rejection.

   #4  Consumer schema audit:
       PASS — ui-default/Pdf.tsx:21 imports BlockViewProps<typeof
       pdfCore.propsSchema> from foundation; Pdf.astro:5 declares
       structurally-equivalent local Props { src; page?; searchable? } that
       matches the schema shape (defaults match the schema defaults at
       :10). Per the "import schemas at v1, never inline z.object"
       memory rule (feedback_cross_package_consumer_pattern.md): Pdf.astro
       does NOT redefine propsSchema with `z.object`; it declares only the
       *structural* TS interface for Astro.props (Astro components do not
       have a Zod runtime surface). The runtime authority remains
       propsSchema, used through serializePdf/parsePdf path. Acceptable.

   #5  Algorithm + runtime constant replication audit:
       PASS — renderPdf is the single authority. Pdf.tsx and Pdf.astro
       both call it. ssr-render.test.ts:25-66 is the 5-row regression
       corpus; iframeSrc construction would byte-diverge against expected
       string if any future edit re-inlined `${src}#page=${page}`.
       Authority-level test (renderPdf itself), not consumer-level test —
       acceptable because both consumers call the authority directly with
       no transformation.

   #6  Sister-file documentation audit:
       PASS — see §2 above. block-pdf/CONTRACT.md vs block-math/CONTRACT.md
       use identical terminology for shared identifiers. New "Wave 3
       search-index 集成" section is D2-specific (no math equivalent
       expected) and does not break sister-doc parity.

   #7  Exception-scope equivalence audit:
       PASS — no try/catch present in any block-pdf source file. Errors
       throw through normally (zod validation in parsePdf/serializePdf,
       schema parse in tests). No replicated exception-handling between
       Pdf.tsx and Pdf.astro since neither has try/catch. This is correct:
       the iframe approach has no in-process failure modes to handle —
       the browser's PDF viewer surfaces its own UI for missing/broken src.

   #8  Authority-document → generated/consumed surface audit:
       PASS — bundle includes:
         - packages/block-pdf/* (the new authority)
         - tsconfig.json:17 (project-references consumer)
         - pnpm-lock.yaml:329-355 (sub-form C: lockfile is generated from
           package.json + pnpm-workspace.yaml)

       No generated `.claude/agents/*.md` or `docs/review-checklist.md`
       changes triggered (block-pdf authority does not modify reviewer
       prompts or `agent-contract.md`). Docs/audits/codex-runs/ contains
