2. REAL BLOCKER #1 — Missing ssr-render.test.ts / ui-default.test.tsx
--------------------------------------------------------------------------------

Wave-2 plan §1041 explicitly mandates three test files:
    Create: packages/block-math/src/__tests__/{core,ui-default,ssr-render}.test.ts

Filesystem reality (packages/block-math/src/__tests__/):
    - core.test.ts                       (6 tests — propsSchema)
    - registry-integration.test.ts       (5 tests — registry round-trip)
    [MISSING] ui-default.test.tsx
    [MISSING] ssr-render.test.ts

Why this matters (ADR-0006 item #5 — algorithm replication audit):

CONTRACT.md:51-52 claims:
    "Math.tsx 与 Math.astro 共调同一函数，editor / SSR / NodeView byte-equivalent"

Source reality:
    - Math.tsx:13-19 wraps katex.renderToString in renderMath() with options
      { displayMode, throwOnError: false, output: 'html', strict: 'ignore' }
    - Math.astro:11-16 inlines katex.renderToString with the **same** option
      object literal — but does NOT call renderMath. The wrapper function is
      not shared; the option object is replicated.

This is the canonical ADR-0006 #5 pattern: same algorithm + runtime constants
replicated across two consumer files, no regression test enforcing byte-equivalence.
If a future PR changes renderMath options (e.g. strict: 'warn', or trust mode
configuration), Math.astro will silently drift. Wave-1 instance #6 (FOUC IIFE
algorithm replication) is the exact precedent — orchestrator codified this as
ADR-0006 item #5 specifically to prevent recurrence.

The plan-mandated ssr-render.test.ts is the defensive regression test that
makes byte-equivalence a CI invariant rather than a CONTRACT assertion. It is
absent. The CONTRACT claim therefore has no enforcement.

Required fix (one of):
  (A) Add ssr-render.test.ts that renders the same {expression, display}
      tuples through Math.tsx (renderToStaticMarkup) AND Math.astro container
      (or directly through katex with the same options) and asserts the
      KaTeX-emitted HTML is byte-equal. Plus a fixture corpus covering at
      least: simple inline, display, multi-line, malformed (error path).
  (B) Refactor Math.astro to import + call renderMath from Math.tsx (removing
      the option-object replication entirely), making byte-equivalence a
      single-authority guarantee at the source level rather than test level.

  Option (B) is structurally stronger and tracks ADR-0006 item #5's preferred
  resolution (eliminate replication where possible; test byte-equivalence
  where unavoidable). Worth coordinating with the worker on whether
  Astro frontmatter can call into a sibling .tsx export.

  Either way, both files must be added to satisfy the plan §1041 AC.

Also missing per plan §1041: ui-default.test.tsx — at minimum should assert
that mathUiDefault.uiId === 'default' (already covered by registry-
integration.test.ts:39 as a side effect, but the plan called for an
independent file). This is lower-severity but still a plan-AC miss.

3. REAL BLOCKER #2 — Sister-doc asymmetry (ADR-0006 item #6)
--------------------------------------------------------------------------------

CONTRACT sister-doc check (block-callout vs block-math):

a) ENTRY COUNT
   - block-callout/CONTRACT.md:8: "四个 entry"
       package.json exports = '.', './core', './ui-default', './ui-default/callout.css'
   - block-math/CONTRACT.md:8: "三个 entry"
       package.json exports = '.', './core', './ui-default'
       (math.css exists at src/ui-default/math.css but is NOT in the exports map)

b) CONSUMER CSS-IMPORT CONTRACT
   - block-callout/CONTRACT.md:26 explicitly tells consumers:
       "消费方 (apps/site / editor-shell) 必须在启动时 import 一次：
        import '@skb/block-callout/ui-default/callout.css';"
   - block-math/CONTRACT.md only says "math.css（design-token-bound）" at
     line 20. It does not document any consumer-side import path or
     obligation. Apps/site SSR + editor-shell will not know they MUST import
     '@skb/block-math/ui-default/math.css' to get the .katex-error styling
     that CONTRACT.md:60 promises.

c) DESIGN-TOKENS DEPENDENCY
   - block-callout/package.json:19 declares "@skb/design-tokens": "workspace:*"
     because callout.css uses --color-* tokens.
   - block-math/package.json declares NO @skb/design-tokens dependency, yet
     math.css uses var(--color-fg), var(--color-error), var(--space-*),
     var(--radius-sm), var(--font-mono) — five token families.

   This is a dead-dep INVERSE: the consumer-CSS depends on tokens, but the
   package doesn't declare the dependency. ADR-0008 D1 Option-A grep would
   not catch this (no JS-import to grep), but the structural promise is the
   same — the package consumes a workspace package and must declare it.
   Without the dep, apps/site does not get a transitive guarantee that
   design-tokens is in the dependency graph; the CSS variables may resolve
   to "undefined" (hot-reload churn risk + colour fallback).

   The block-callout sister sets the precedent for this exact issue and
   handles it correctly. block-math diverges silently.

This trio of asymmetries is exactly ADR-0006 item #6 (one CONTRACT.md is
updated; sister CONTRACT.md drifts). Wave-1 instance #5 had the same shape
(agent-tools CONTRACT lagging behind editor-commands). render-block-eng
inherited the callout template structure but did not propagate the post-C1+C2
template refinements (CSS subpath export + design-tokens dep declaration +
consumer-import contract).

Required fix:
  i.   Add "./ui-default/math.css": "./src/ui-default/math.css" to
       packages/block-math/package.json#exports.
  ii.  Add "@skb/design-tokens": "workspace:*" to packages/block-math/package.json#dependencies.
  iii. Update CONTRACT.md:8 from "三个 entry" to "四个 entry" and add the
       fourth bullet describing math.css.
  iv.  Add consumer-import obligation to CONTRACT.md (mirror callout
       CONTRACT:26): "消费方必须 import '@skb/block-math/ui-default/math.css'
       一次" — including apps/site + editor-shell.
  v.   pnpm install + commit refreshed pnpm-lock.yaml (lockfile-as-generated
       artifact per ADR-0006 item #8 sub-form C; lesson from
       feedback_git_operator_explicit_stage memory).

Item #4 — Consumer schema audit (single-authority schema, no inline duplicates):
  PASS. mathCore.propsSchema is the single authority. Consumer files:
    - parse.ts:26 imports + calls propsSchema.parse — no inline z.object
    - serialize.ts:26 imports + calls propsSchema.parse — no inline z.object
    - math.ui.ts uses BlockViewProps<typeof mathCore.propsSchema> — type-only
      reference, no schema redefinition
    - Math.tsx uses BlockViewProps<typeof mathCore.propsSchema> — same
    - Math.astro inlines its own Props interface (expression: string,

      propsSchema changes (e.g. add 'macros' attribute → Math.astro's Props
      interface won't gain it; SSR can pass through wrong-typed props
      without validation). MINOR — flag for follow-up. Not a blocker for
      this PR but worth tracking; acceptable to defer if a fixture-driven

      Astro frontmatter (consider Wave 3).
