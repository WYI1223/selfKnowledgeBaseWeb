## Instruction Priority

Superpowers skills override default system prompt behavior, but **user instructions always take precedence**:

1. **User's explicit instructions** (CLAUDE.md, GEMINI.md, AGENTS.md, direct requests) — highest priority
2. **Superpowers skills** — override default system behavior where they conflict
3. **Default system prompt** — lowest priority

If CLAUDE.md, GEMINI.md, or AGENTS.md says "don't use TDD" and a skill says "always use TDD," follow the user's instructions. The user is in control.

## How to Access Skills

**In Gemini CLI:** Skills activate via the `activate_skill` tool. Gemini loads skill metadata at session start and activates the full content on demand.

**In other environments:** Check your platform's documentation for how skills are loaded.

# Using Skills

## The Rule

**Invoke relevant or requested skills BEFORE any response or action.** Even a 1% chance a skill might apply means that you should invoke the skill to check. If an invoked skill turns out to be wrong for the situation, you don't need to use it.

## Red Flags

These thoughts mean STOP—you're rationalizing:

| Thought | Reality |
|---------|---------|
| "This is just a simple question" | Questions are tasks. Check for skills. |
| "I need more context first" | Skill check comes BEFORE clarifying questions. |
| "Let me explore the codebase first" | Skills tell you HOW to explore. Check first. |
| "I can check git/files quickly" | Files lack conversation context. Check for skills. |
| "Let me gather information first" | Skills tell you HOW to gather information. |
| "This doesn't need a formal skill" | If a skill exists, use it. |
| "I remember this skill" | Skills evolve. Read current version. |
| "This doesn't count as a task" | Action = task. Check for skills. |
| "The skill is overkill" | Simple things become complex. Use it. |
| "I'll just do this one thing first" | Check BEFORE doing anything. |
| "This feels productive" | Undisciplined action wastes time. Skills prevent this. |
| "I know what that means" | Knowing the concept ≠ using the skill. Invoke it. |

## Skill Priority

When multiple skills could apply, use this order:

1. **Process skills first** (brainstorming, debugging) - these determine HOW to approach the task
2. **Implementation skills second** (frontend-design, mcp-builder) - these guide execution

"Let's build X" → brainstorming first, then implementation skills.
"Fix this bug" → debugging first, then domain-specific skills.

## Skill Types

**Flexible** (patterns): Adapt principles to context.

The skill itself tells you which.

   358	(non-prose component blocks). Documented as the answer to Q1.
   359	
   360	### D2 — Floating menu rendered inline (no React Portal); position: absolute relative to button
   361	
   362	Two architectural choices for the menu floating layer:
   363	- **Option A**: React Portal to `document.body` + manual coordinate
   364	  computation (anchored to the button's `getBoundingClientRect()`).
   365	  Robust against parent overflow:hidden / transform; standard for
   366	  popovers in production UIs.
   367	- **Option B**: render inline within the kebab button's React tree
   368	  + `position: absolute` relative to `.skb-block-nodeview__kebab-wrapper`.
   369	  No portal mount complexity; coordinates handled by CSS.
   370	
   371	**Decision**: Option B for cf-20e MVP. Rationale:
   372	1. cf-20e is dependency-light (no portal library, no manual
   373	   `getBoundingClientRect` math).
   374	2. The cf-19 gutter shell is `position: absolute; top: 4px` already;
   375	   the kebab button + its menu inherit this positioning context
   376	   naturally.
   377	3. The menu's `z-index: 10` lifts it above adjacent blocks; the
   378	   `.skb-grid .ProseMirror` editor surface doesn't have
   379	   `overflow: hidden` so the menu is not clipped.
   380	4. Future cf-22 / cf-23 may switch to Option A (portal) if cross-
   381	   block menu overflow becomes an issue (e.g. menu near grid edge
   382	   gets clipped); cf-20e ships the simpler version.
   383	
   384	**Risk**: a menu near the bottom of the editor surface may render
   385	below the viewport. Acceptable for cf-20e (user can scroll); cf-22
   386	will add edge-detection + flip-up logic if needed.
   387	
   388	### D3 — Change-kind attr translation: drop-and-default + preserve grid attrs only
   389	
   390	**Open question Q3 from dispatch brief**: drop-and-default vs
   391	preserve-compatible-fields.
   392	
   393	**Decision**: drop-and-default + preserve grid attrs only. Rationale:
   394	1. Cross-kind attr translation is meaningful only for SOME pairs.
   395	   Examples: callout↔code share semantic "title-like" fields
   396	   (title vs filename); pdf↔image share spatial fields (src,
   397	   width, height) but not semantic ones (page vs alt). Most pairs
   398	   share NOTHING (math expression vs jupyter code, nn-viz layers
   399	   vs agent-flow nodes/edges, etc.).
   400	2. A general N×N translation table is high-effort to maintain
   401	   correctly + introduces silent data corruption when pairs added
   402	   later forget translation entries. Drop-and-default is
   403	   structurally simpler + the user can copy-paste useful content
   404	   from the previous block before changing kind if needed.
   405	3. Grid attrs (`col`, `row?`, `colSpan`, `rowSpan`) are universal
   406	   across ALL block kinds + represent the user's spatial intent
   407	   that survives a kind change. Preserving them keeps the
   408	   visually-placed block at the same spot post-change.
   409	
   410	**Implementation**: pure helper `buildChangeKindAttrs(sourceAttrs,
   411	targetKind, targetDefaults)`:
   412	- Start with `{...targetDefaults}` (the new kind's defaults).
   413	- Override with the source's `col`, `colSpan`, `rowSpan`, `row`
   414	  (only if defined) — these 4 fields preserved.
   415	- All other source fields dropped silently.
   416	
   417	**Side effect**: if user picks "Change kind… → same kind" (e.g.
   418	callout → callout), the result is the target kind's defaults +
   419	preserved grid — a "reset to defaults" path. Document as an
   420	intended affordance (the user CAN use it to reset block content
   421	without changing kind).
   422	
   423	### D4 — Silent delete (no confirm dialog); user can Cmd+Z to undo
   424	
   425	**Open question Q4 from dispatch brief**: confirm-on-delete vs
   426	silent.
   427	
   428	**Decision**: silent. Rationale:
   429	1. Matches Notion / Tiptap default behavior — no friction-adding
   430	   confirmation for routine block operations.
   431	2. Tiptap's built-in `history` extension (part of StarterKit)
   432	   provides Cmd+Z / Cmd+Shift+Z undo/redo; deleted blocks recover
   433	   via Cmd+Z (typically a single keypress).
   434	3. Confirm dialogs are cf-22 a11y / UX-polish scope; cf-20e ships
   435	   the minimal action set.
   436	
   437	Documented in PR.md + CONTRACT.md so future a11y review can amend
   438	if user testing reveals confirm-dialog need.
   439	
   440	### D5 — Imperative actions via React context (consumer closures over Tiptap editor)
   441	
   442	The kebab button is presentational; the actual Tiptap mutations
   443	(deleteNode / insertContent / setNodeMarkup) need the live editor.
   444	Two architectural choices:
   445	- **Option A**: pass `editor` directly to `<KebabButton editor={...}>`
   446	  via prop drilling. Requires `BlockNodeView` to receive the
   447	  editor (it has access via Tiptap's `props.editor` from
   448	  `ReactNodeViewProps`).

   450	  `{onDelete(blockId), onDuplicate(blockId), onChangeKind(blockId,
   451	  newKind)}` callbacks; the consumer (`EditorShellMount.tsx`)
   452	  closures over `editor` and provides the context value. Mirrors
   453	  cf-20c-2 `DragDropContext` + cf-20d `ResizeContext` pattern
   454	  exactly.
   455	
   456	**Decision**: Option B — consistency with cf-20c-2 + cf-20d
   457	patterns + keeps `KebabButton` editor-agnostic for testability.
   458	The consumer is the single owner of editor mutations across all 3
   459	contexts (drag, resize, kebab); the per-block components stay
   460	purely presentational.
   461	
   462	### D6 — Duplicate fires success-pulse via cf-20c-2 dropEpoch reuse (Option B from cf-20d D3)
   463	
   464	Per cf-20c-2 R3 reflection ("the dropEpoch pattern is the canonical
   465	'rapid-action animation isolation' pattern. cf-20d resize will
   466	adopt the same pattern for its own resize-success pulse"), cf-20e
   467	duplicate ALSO routes the success-pulse through
   468	`pipeline.setLastDroppedFromExternal(blockId, rect)`. The pulse
   469	visually anchors at the duplicated block's bounding rect after
   470	2-rAF re-measure (post-Tiptap commit + browser layout). Delete +
   471	change-kind do NOT fire pulses (delete removes the block; change-
   472	kind keeps the block in place — no positional change to celebrate).
   473	
   474	### D7 — `node.toJSON()` for duplicate (Tiptap canonical pattern); fresh PM positions assigned automatically
   475	
   476	Tiptap's `node.toJSON()` returns the canonical serialized
   477	representation; `editor.chain().insertContentAt(pos + nodeSize,
   478	nodeJson).run()` re-creates a structurally identical node at the
   479	new position with fresh ProseMirror positions (the inserted node
   480	gets a new `pos` per ProseMirror's internal indexing). Future

   488	### D8 — Click-outside detection via `useEffect` mousedown listener on `document` (no library)
   489	
   490	The floating menu must close on click-outside-the-menu. Standard
   491	React pattern: `useEffect` adds a mousedown listener to `document`;
   492	the handler checks if `event.target` is inside the menu's
   493	`useRef` container; if NOT, closes the menu. Esc-to-close is a
